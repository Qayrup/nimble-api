# nimble-api 修复方案（2026-08-16）

## 审查范围与方法

- 对象：nimble-api 6 子包（api-service / eventhub / oidc / sse-service / node-adapter / api-extend），约 1 万行源码。
- 流程：初审（general-purpose 子代理）产出 26 个候选优化项 → **全部用 opus 模型独立核验**（3 批并行，逐项读源码验证成立性/影响/更优方案）。
- 结论：26 项中 3 项误报、1 项部分成立、其余成立。下表仅列值得处理的项。

---

## P1 — 必改（安全 / 正确性）

### P1-1 `node-adapter` 跨源重定向转发凭据（安全）
- **位置**：`node-adapter/src/adapter.ts:331-351`（`nextConfig` 保留原 headers）+ `:106`（透传）
- **问题**：301/302/303/307/308 重定向到**不同 host** 时，`Authorization`（Bearer token）与手写 `Cookie` 头原样发往第三方源——**凭据泄露**。cookie jar 按新 URL 匹配无此问题，泄漏点在 headers 透传。
- **方案**：重定向时比较 `new URL(newUrl).origin` 与 `new URL(config.url).origin`；跨源则剥离 `Authorization` / `Cookie` / `Proxy-Authorization`（及敏感自定义头）。
- **风险**：低（同源语义不变，仅跨源剥离）。

### P1-2 `api-service` 缓存键碰撞（正确性）
- **位置**：`api-service/src/utils/cache-key.ts:18-23`（`stableNormalize`）+ `:41,44`（`JSON.stringify`）
- **问题**：`Object.keys(new Date())` / `new Map()` / `new Set()` 均为 `[]`，`stableNormalize` 把它们全部归一为 `{}` → 不同 Date（如 `params: { startDate: d1 }` vs `d2`）生成**相同 cacheKey → 返回错误缓存数据**。金价/数据平台按日期区间查询为常见形态。
- **方案**：`stableNormalize` 增加类型分支——`Date` → `.toISOString()`；`Map` → `[...m].sort()` 数组；`Set` → `[...s].sort()`；`undefined` 用哨兵占位避免空对象假碰撞。或改用 `json-stable-stringify`。
- **风险**：低（仅影响缓存键生成，行为更正确）。

### P1-3 `api-service` 超时/取消误判为 `ERR_NETWORK` 并重试
- **位置**：`adapters/fetch.ts:16-18,25`（超时与用户 abort 都调 `controller.abort()`）+ `client.ts:435-438,467-472`
- **问题**：fetch 适配器内部超时和用户取消无法区分，都产生 `AbortError` → 被 `#executeWithRetry` 包成 `ERR_NETWORK`(status 0)；`shouldRetry` 对 status 0 恒真，且合并 signal `aborted` 为 false → **单次超时被无谓重试 limit 次**（~90s+）。与 `xhr.ts`（明确 `ERR_TIMEOUT`）不一致。
- **方案**：fetch 引入 `let timedOut = false`，超时回调置位；catch 中 `timedOut → ERR_TIMEOUT`、`signal.aborted → ERR_ABORTED`；`#executeWithRetry` 对 `ERR_TIMEOUT`/`ERR_ABORTED` 不参与重试。
- **风险**：中（改变现有重试语义——超时不再重试，需确认）。

## P2 — 建议修

### P2-1 `oidc` 无存储时跳过 state/PKCE（登录 CSRF）
- **位置**：`oidc/OidcClient.ts:90-99,114`
- **问题**：sessionStorage 不可用（隐私模式/webview）时 `expectedState=null` → state 校验与 code_verifier 均跳过 → **login CSRF** + 服务器强制 PKCE 时登录直接不可用。
- **方案**：fail-closed——无存储则拒绝登录（抛 `OidcUnavailableError`）；至少 state 校验不应因无存储而跳过。

### P2-2 `oidc` `importToken` 未接线自动刷新/跨标签同步
- **位置**：`oidc/OidcClient.ts:210-219`（新方法）
- **问题**：相比 `handleCallback`/`silentRefresh`，`importToken` 未调用 `#scheduleAutoRefresh()` 与 `#sync.broadcast()` → 导入的短命 token 到期无静默续期、其它标签页不同步。
- **方案**：补两行——`this.#scheduleAutoRefresh()`；有 token 则 `this.#sync.broadcast(token, source)`。

### P2-3 `oidc` `refreshTokenMode:'cookie'` 是死配置
- **位置**：`oidc/types.ts:10` + `token-store.ts:42-52`
- **问题**：配置声明了但 `OidcClient`/`TokenStore` 从未读取；实际行为恒为 memory，刷新 token 只存内存，页面刷新后 `silentRefresh()` 返回 null → 会话提前失效。
- **方案**：**需确认**——真正实现 cookie 模式需后端配合设置 HttpOnly cookie（前端 JS 无法写 HttpOnly）。若不实现，在类型注释明确「当前仅 memory 生效」，避免误用。

### P2-4 `sse-service` `maxAttempts` 在抖动场景失效
- **位置**：`sse-service/sse.ts:267` + `:294-301`
- **问题**：`#dispatch` 每条消息把 `reconnectAttempts` 清零，导致「服务端接受→发 1 条→断连」抖动下 `maxAttempts` 永不触发 → 无限重连。
- **方案**：删除 `#dispatch` 里的归零，仅保留 `#armStabilityTimer`（连接稳定满 baseInterval 才算成功归零）。

### P2-5 `sse-service` `#buffer` 跨重连残留
- **位置**：`sse-service/sse.ts:19,259`
- **问题**：连接在事件中间断开（残留半行），重连后新流首字节拼到旧半行 → 重连后首条事件损坏。
- **方案**：`#connect()` 入口 `this.#buffer = ''`（每次重连清空残行）。

### P2-6 `sse-service` 错误分支泄漏响应流
- **位置**：`sse-service/sse.ts:160-167`
- **问题**：`!res.ok` / Content-Type 不符时抛错未 cancel `res.body` → 底层 socket 挂起，重试场景放大泄漏。
- **方案**：两条抛错路径前 `await res.body?.cancel()`；读取循环 catch 也 cancel reader/body。

### P2-7 `eventhub` throttle+debounce 组合取消泄漏
- **位置**：`eventhub/src/event-hub.ts:1217-1242`（#wrapHandler/#cancelHandler）
- **问题**：包装顺序 throttle(内)→debounce(外)，`#cancelHandler` 只清外层；内层 throttle trailing timer 仍触发 → `off()`/`unsub()` 后 handler 仍被调用。
- **方案**：取消沿包装链传导——各 wrapper 记录内层引用，`#cancelHandler` 递归清所有 `_timer`/`_cancelled`（或共享取消令牌）。

### P2-8 `eventhub` meta 延迟队列排空异常
- **位置**：`eventhub/src/event-hub.ts:1275-1277`
- **问题**：排空循环 `while(shift()!())` 中 handler 抛错冲出，剩余 deferred meta 滞留 → 下次错位补发，破坏 meta 顺序。
- **方案**：排空循环逐个 try/catch，记录首个错误并继续排空，最后再抛。

## P3 — 低优先（边界 / 体验）

| 库 | 项 | 方案 |
|----|----|------|
| api-service | typed.ts `invoke()` 同步抛错时 pending 泄漏 | inc 后 try/catch，抛错时 `dec()`（或 switch 前校验 method 白名单） |
| api-service | `responseType:'stream'` 静默降级 JSON.parse | fetch/xhr/uniapp 对 `'stream'` 显式抛 `ERR_BAD_RESPONSE` 或收窄类型 |
| api-service | 非 JSON 错误体丢响应头 | headers 解析提到 body 解析前，data 放原始 text |
| api-service | backoff `+Math.random()*200` 可超 maxDelay | 改为 `Math.min(delay + jitter, max)` |
| api-service | fetch progress no-op（已文档化） | 传入时 console.warn 提示用 XHR adapter |
| api-service | exportState 循环引用 JSON.stringify 抛 | replacer 加 WeakSet 循环检测 / try-catch 降级 |
| eventhub | `events()` 并发 next() 悬挂 | 文档声明必须顺序 await，或 pending resolver 队列化 |
| eventhub | `maxListeners:'throw'` 留空键 | 抛错后 `list.length===0` 则 delete(event) |
| eventhub | `listenerCount` 不含 any-handler | `listenerCount` 加 `anyHandlers.length` 对齐 `hasListeners` |
| api-extend | concurrency `NaN` 校验漏 | `if (!Number.isFinite(limit) || limit < 1) throw` |
| api-extend | poll 抛错即中断 | **需确认**：若设计意图则 JSDoc 注明，否则加 `retryOnError` |

## 误报（opus 排除，不改）

- **dedup + pending 泄漏**（api-service/typed.ts）：每个调用方各自 inc/dec 绑定同一 promise，计数对称。
- **interruptibleSleep 永不 settle**（api-service/client.ts）：入口已有 `signal?.aborted` 早退 + 单线程同步窗口 + 调用方二次兜底。
- **glob 转义缺 `[`**（eventhub/utils/glob.ts）：正则字符类内 `[` 是字面量，实测正确。
